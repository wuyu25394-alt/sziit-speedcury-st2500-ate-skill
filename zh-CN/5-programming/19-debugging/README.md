## 三类故障，三条不同的路

程序上机第一次跑，出的问题大多不是「代码写错了」，而是「有一样东西没到位」。它们可以按现象分成三类：**连不上**、**不生效**、**对不上**。

分清类别比记住答案重要，因为三类故障的排查方向完全不同：

| 现象 | 归类 | 先动哪里 |
|---|---|---|
| 界面一直 `connecting..`，反复重连 | 连不上 | 关多余实例、清残留进程 |
| 改了代码重编译，结果一点没变 | 不生效 | 看 DLL 时间戳、工程路径 |
| 程序崩在 `CheckResultAndBin` | 对不上 | 数 `.tmf` 子项与 `count` |
| 读数离谱但稳定 | 对不上 | 量程、延时、模式 |
| 工程加载失败，提示很少 | 不生效 | 查 `.tmf` 结构 |

五种具体故障里只有最后一种会明确报错，其余常常「看起来在正常工作」——界面在转、编译成功、程序也在跑，只是跑的不是你要的东西。

## 连不上：先数一数有几个自己在抢

`connecting..` 卡住不动，或者反复重连，十有八九不是网线，而是**连接被占了**：同一台机器同一时刻只认一个上位机实例。开着两个 IDE，或者上一次退出时进程没走干净，新的那个就只能一直排队。处理顺序固定：

1. 关掉全部上位机窗口，包括后台进程。
2. 只开一个实例，重新连。
3. 连上了先看 Runner Console 与 Log，确认是真的连上，而不是又转一圈。
4. 连接异常但窗口还在响应时，用 **Tester → Runner** 重启 Runner，不必重装软件。

> [!NOTE]
> **📖 名词｜Runner**
>
> - **定义**：真正执行测试的后台进程，界面只负责编辑与下发。
> - **现场用法**：「Runner 挂了，界面还活着。」——重启 Runner 而不是重启整台机器。
> - **相关名词**：Job、Load、Prj Run、Runner Console
> - **常见混淆**：把界面当成执行者。按开始只是发指令，执行在 Runner 里；「界面正常但跑不动」是常态。

> [!TIP]
> **🔧 Know-how｜先看日志，再决定要不要重开**
>
> - **情境**：`connecting..` 时好时坏，重开一次能好一会儿。
> - **做法**：先打开 Runner Console 与 Log，把 Runner Log Level 调到 DEBUG 复现一次，看清最后一条再重启。
> - **为什么**：重开会把现场擦掉，同一个故障下次还得从头猜。
> - **没做会怎样**：反复重装软件，真正的原因——另一个实例占着连接——一次也没被看见。
> - **相关章节**：[第 16 章 工程文件体系](../16-project-files/README.md)

## 不生效：DLL 的时间戳比代码旧

改了 `Test.cpp`，Build 提示成功，`Prj Run` 跑出来的结果和改之前一模一样。先别怀疑逻辑，看两样：**DLL 的时间**，和**它是不是程序正在用的那一个**。

`Test.cpp` 编译出 `Test.dll`，`.job` 声明测试库的位置。「不生效」有两类根因：编译产物没被拷贝或覆盖；程序跑的是另一份目录里的旧 DLL——换机器、复制工程、改路径，都会出现「两个自己」。工程路径换机器后要改三处，少改一处就回到上面那一类：

| 文件 | 要改的字段 |
|---|---|
| `.job` | `AteHomePath`、`jobDir`、`jobFilePath` |
| `Makefile` | `RUNNER_HOME`（默认 `d:/MINI-ATE/runner`） |
| `.cproject` | include 路径（`D:/MINI-ATE/runner/inc` 与 MinGW 路径） |

改代码的标准动作是**先 Unload，再 Build，再 Load**。只 Build 不 Unload，已经加载的旧 DLL 还在内存里跑。

> [!NOTE]
> **📖 名词｜Test.dll**
>
> - **定义**：`Test.cpp` 编译出的动态库，`.job` 声明的测试库就是它。
> - **现场用法**：「这次改的没进去，看 dll 时间。」——一句话点出问题在哪一层。
> - **相关名词**：Build Tool、Makefile、Load、Unload
> - **常见混淆**：以为 Build 成功就等于改动生效。Build 只保证编译过，不保证这一份被程序加载。

> [!TIP]
> **🔧 Know-how｜用时间戳确认「跑的是这一版」**
>
> - **情境**：改完一处判据，重编译后结果毫无变化。
> - **做法**：看 `Test.dll` 的修改时间是不是刚才；再看 `.job` 指向的是不是你当前的工程目录。
> - **为什么**：编译成功和加载成功是两件事，中间隔着一次拷贝和一次 Unload／Load。
> - **没做会怎样**：在旧 DLL 上反复调参，最后不知哪一版是对的。
> - **相关章节**：[第 17 章 Test.cpp](../17-test-cpp/README.md)、[第 16 章 工程文件体系](../16-project-files/README.md)

## 对不上：数出来了，但不是你以为的那个数

这一类最费时间：程序不崩、界面不红，只是数字不对。常见四种：

**一、崩在 `CheckResultAndBin`。** 根因几乎总是同一件事：`.tmf` 声明的结果参数个数，和代码里传的 `count` 不一致。只崩算好，更阴的是反过来——声明了 6 个参数，代码只判前 5 个，最后那个**永远不判限**。

**二、起点不对。** `ParamID` 从 0 开始：`.tmf` 里第一个子项对应的是 0，不是 1。从中间某个子项开始判，得同时给起始编号和个数。

**三、单位对不上。** `.tmf` 里写 V，代码里给 mV，判据差 1000 倍；或者把 Min／Max 填成了裸数字，`.tmf` 该有的 Site 层也缺了——这类问题会让工程加载失败，而提示只有很少几个字，看着像软件坏了。

**四、量程、延时与模式。** 小电流直接上小量程，上电瞬态会让读数超量程；继电器刚合上就测，读到的是还没稳的值，常见的等待是 8～10 ms。

> [!TIP]
> **🔧 Know-how｜参数个数从 `.tmf` 数回来**
>
> - **情境**：`CheckResultAndBin` 抛异常，或者判限结果明显不对。
> - **做法**：打开 `.tmf` 的 ResultAnalysis，数这一项下面的子项个数，再对照代码里的 `count`；顺序也要对，下标就是按 `.tmf` 排的。
> - **为什么**：判定是拿测量结果向量按下标去对限值的，个数与顺序是唯一的契约。
> - **没做会怎样**：要么越界崩掉，要么漏判最后几项——后者会一路带到量产。
> - **相关章节**：[第 16 章 工程文件体系](../16-project-files/README.md)

## 一条可以照着走的排查顺序

前面讲「哪里会错」，这一段讲「按什么顺序查」。原则：先排除整条链断掉，再查这一项的数不对——**机器通 → 资源在 → 工程开 → DLL 新 → 参数齐 → 最后怀疑判据**。

| 顺序 | 查什么 | 怎么确认 |
|---|---|---|
| 1 | 机器通 | 看报警监测球（绿正常、红故障），双击进机箱监测「获取异常」；必要时跑自检 |
| 2 | 资源在 | 看 `.res` 自检结果与 `.sig` 的 AFEType：这块板、这个通道在不在位 |
| 3 | 工程开 | 先 Build 再 Load，工程不变红；一次只 Load 一个；确认没有第二个实例 |
| 4 | DLL 新 | `Test.dll` 时间戳是刚才，`.job` 指向的目录就是当前工程 |
| 5 | 参数齐 | `.tmf` 的子项数、`count`、`ParamID` 起点、单位，四样对齐 |
| 6 | 判据 | 最后才收紧或怀疑限值本身 |

为什么判据放最后：前三步任一不通，后面读数都没有意义；DLL 不新，你查的是上一版代码；参数不齐，判据根本没被用上。**判据最容易被怀疑，却最少是根因。**

最有用的是日志，不是界面上的红字。Datalog 里失败值会标红，能看出是整项 fail 还是个别点；Text Log 按测试项目分类，比表格式的 Datalog 更容易定位到具体一项。读数为 0、超时、量程溢出，往往只在日志里留一句，界面上看不见。

---

## 本章重点

1. 三类故障分开查：连不上看进程与实例，不生效看 DLL 与路径，对不上看参数契约。
2. `connecting..` 反复重连，先查第二个实例或残留进程，再谈硬件。
3. 改了 `Test.cpp` 要 **Unload → Build → Load**，并用 `Test.dll` 时间戳确认跑的是这一版。
4. `CheckResultAndBin` 的 `count` 必须等于 `.tmf` 的子项数，`ParamID` 从 0 开始；个数少了会漏判，而且不报错。
5. 排查顺序固定为「机器通、资源在、工程开、DLL 新、参数齐」，判据永远放最后。
