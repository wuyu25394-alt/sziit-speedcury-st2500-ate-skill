# 附录 B　现场踩坑清单

这些条目来自实际调试记录。按「现象 → 最可能的原因 → 怎么查」组织，**遇到问题时从最上面一条往下排除**，比自己猜快得多。

一条通用原则：**先分三类**——连不上（通信层）、不生效（文件与编译层）、对不上（测量与判据层）。分错类，查多久都是白查。

---

## B.1 连接与环境

| 现象 | 最可能原因 | 怎么查 |
|---|---|---|
| 软件一直显示 `connecting..`，每隔几秒重连一次 | 同时开了多个实例，或有残留进程占着连接 | 关掉全部实例，用任务管理器确认相关进程都已退出，再只开一个 |
| 上次正常，这次怎么都连不上 | 上一轮没退干净，后台还有进程 | 按进程名（不是窗口）找，把该目录下的进程全部结束 |
| 插上机器，软件就是不认 | 板卡未在位（OffLine）、槽位没配、服务未启动 | 先看板卡状态灯，再在资源自检里确认这块板在不在列表里 |
| 换了一台机器，工程打不开 | 工程里的资源配置与目标机器不一致 | 重新做一次资源自检，再核对 `.sig` 里引用的资源类型是否存在 |
| 测试跑到一半掉线 | 供电或接地问题、接口板接触不良 | 看是否固定在某一项或某一工位；换接口板/线缆对比 |

> [!TIP]
> **🔧 Know-how｜先确认「只有一个」**
>
> - **情境**：连着测都正常，突然开始反复重连。
> - **做法**：把所有相关进程结束干净，只启动一个实例，等它连上再操作。
> - **为什么**：测试机同一时刻只服务一个连接。第二个实例起来，两个互相抢，谁都连不稳。
> - **没做会怎样**：以为机器坏了，反复重启、重装软件，其实只是多开了一个窗口。

## B.2 编译与加载

| 现象 | 最可能原因 | 怎么查 |
|---|---|---|
| 改了代码、重编译了，跑出来还是旧结果 | 运行的 DLL 不是你刚编出来的那个 | 比对 DLL 的修改时间，确认它落在**当前工程实际加载的目录** |
| 编译通过，运行时找不到函数 | 导出名或调用约定不一致 | 确认函数用 `extern "C"` 导出，且声明与 `interface.h` 一致 |
| 工程能打开，但测试项跑不起来 | `Test.dll` 缺失或位数不对 | 看工程目录里有没有 DLL，再看它的位数与平台是否匹配 |
| 加载工程时报错，提示含糊 | 工程文件结构不对（缺层级、类型写错） | 用同版本的正常工程做对照，逐键比对结构 |
| 换了台电脑，工程里的路径全失效 | 绝对路径 | 改用相对路径或重新指定工程目录 |

> [!TIP]
> **🔧 Know-how｜「没生效」先看时间戳**
>
> - **情境**：改完代码，跑出来的判据、bin、日志全都是旧的。
> - **做法**：看 DLL 的修改时间是不是刚才那一次；再确认工程实际加载的目录是不是你编译的那个目录。
> - **为什么**：一个产品常有多个副本目录（旧版本、备份、另一个盘的克隆），编译器和测试程序各指一个。
> - **没做会怎样**：一直改代码、一直没效果，最后发现改的是另一份。

---

## B.3 测量与判据

| 现象 | 最可能原因 | 怎么查 |
|---|---|---|
| 读数明显离谱（差几个数量级） | 量程选错、单位换算错、模式选错 | 先对照量级看是否合理，再逐项核对量程与模式 |
| 读数在小电流档乱跳 | 建立时间不够、线缆漏电、继电器漏电 | 加长延时看是否稳定；换短一点的线；避开受污染的通路 |
| 同一项两次测结果差很多 | 没等稳定就读、接触电阻变化 | 固定延时后对比；检查接口板与插座 |
| 测电压时读数偏大，且随电流增大 | 用了两线接法测大电流 | 改用四线，把 Sense 线单独跨到被测件两端 |
| 某几项全 fail，其他都正常 | 判据单位写错（µA 写成 mA、mV 写成 V） | 逐条核对判据与数据手册的单位 |
| 数值全在窗口内但整体偏移 | 测试条件与手册不一致（VDD、温度、负载） | 找出条件差异，不要急着改判据 |
| 某个通道永远 fail | 该通道的继电器、探针、走线有问题 | 把测试项换到另一个通道试，能定位是通道还是器件 |

> [!TIP]
> **🔧 Know-how｜先看量级，再看小数**
>
> - **情境**：某一项读数不对，盯着小数点后第三位研究。
> - **做法**：先判断量级对不对（漏电该是 µA 量级，不该是 mA），量级对了再看精度。
> - **为什么**：量级错通常是模式、量程、单位这类结构性问题，一次改对；精度差往往是系统性的噪声与建立时间问题，要慢慢调。
> - **没做会怎样**：在噪声里找规律，调一天也没有进展。

## B.4 工程文件

| 现象 | 最可能原因 | 怎么查 |
|---|---|---|
| 结果判定全 pass，或全 fail | 声明的结果参数个数与代码里传的数量不一致 | 数一遍 `.tmf` 里该测试项的结果参数，与代码里的计数常量对比 |
| 结果参数从第几个开始对不上 | 起始序号（StartParamNumber）写错 | 确认每个测试项的结果参数在文件里的起点 |
| bin 分布异常，某一类特别多 | bin 号冲突、默认 bin 写错 | 检查各测试项的 bin 分配有没有重复 |
| 声明了参数，但取不到值 | 参数名不匹配（大小写、空格、全半角） | 逐字符比对，不要凭记忆 |
| 某测试项被跳过 | 该 Func 没启用到流程里，或 LoopCount 为 0 | 看流程里这一项在不在执行列表 |
| 改判据没反应 | 改的是另一份工程文件的副本 | 确认编辑的文件就是工程实际加载的那一份 |

> [!TIP]
> **🔧 Know-how｜配置和代码，谁说了算要写清楚**
>
> - **情境**：一个测试项，判据在配置文件里，判定在代码里。
> - **做法**：约定「配置只放限值，代码只放算法与判定」，两边靠参数编号对齐，编号一改两边同时改。
> - **为什么**：两边都能改的事，最后两边都会有人改，而且不会通知对方。
> - **没做会怎样**：代码里判 80 mA，配置里限 50 mA，测出来全 fail，谁都以为是芯片坏了。

## B.5 几个真实的「资料错误」

整理和实测过程中发现的问题，记在这里，遇到时不要怀疑自己：

| 现象 | 真因 |
|---|---|
| 课件给的某项限值与工程里不一致（开短路、VOH、IIL 都有过） | 课件是教学模板，工程是实际产品配置。**以工程与产品要求为准** |
| 某 8 位 ADC 的课件把 ENOB 限值写成 12～16 bit | 物理上不可能。判据必须服从器件规格，不能照抄模板 |
| API 手册没写的资源能力，课件里写了完整规格 | 同一门课的资料要交叉对照：手册给定义，课件给数据 |
| 说明文档把通道三元组写成「板卡:资源:通道」 | 手册的定义是「机头 : 业务板 : 通道」，**不含资源类型层** |

更多条目（含工程源码里的真实 bug）见仓库根目录的 [KNOWN-ISSUES.md](../../KNOWN-ISSUES.md)。
